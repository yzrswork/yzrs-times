# 編集長AI（Gemini）の取り扱いガイド

2026-07-28 作成。編集長として働くGeminiの権限、失敗の受け止め方、指示の変え方、点検方法をまとめる。
設計判断の経緯は DESIGN.md、日々の運用は SETUP.md を参照。

## 1. 編集長の権限と、システムの権限

編集長AIに任せているのは**編集判断だけ**である（紙面憲法5番、6番）。

| 編集長（Gemini）が決めること | システム（決定論的コード）が決めること |
|---|---|
| 記事の選定と並び（top、sections） | 候補の収集、重複除去、Heat計算、クォータ |
| 日本語3行要約（summaries） | URL、タイトル、日付、価格などの事実データ |
| 今日のテーマ（theme） | テーマの重複検出と警告（store.loadRecentThemes） |
| 編集長コメントと今日の見送り（editorial） | 署名の固定文字列 |
| Hidden Gemの選定と理由（hiddenGem） | Gem候補の絞り込み（30日再掲禁止、有名ドメイン除外） |
| カテゴリとキーワード（categories） | キーワードの品質フィルタ（keywords.mjs） |

重要な原則: **編集長は候補IDしか参照できない。** URLも日付も書かせない（幻覚の構造的排除）。
出力はGemini側の responseSchema（ID列挙のenum）と、受け取り側の validateAndRepair の二段で検証される。

## 2. フォールバックの階層（沈黙させない設計）

編集が失敗しても発行は止まらない。失敗は次の順で吸収される。

1. **リトライ**: モデルごとに3回、4秒基点の指数バックオフ（503の波を乗り切る）
2. **モデルチェーン**: sources.json editor.models を上から順に試す
   （現在: gemini-3.5-flash, gemini-flash-latest, gemini-3.1-flash-lite, gemini-flash-lite-latest。
   前段が本命、後段は混雑時に空きやすいlite系）
3. **フィールド単位の修復**: 出力の一部だけ壊れている場合、壊れたフィールドだけ
   システム側の妥当値で埋める（validateAndRepair。例: summariesが欠けた記事はsnippetから機械要約）
4. **完全フォールバック**: 全モデル失敗時はHeat順の自動編成で発行する
   （テーマは『編集部より』、コメントで「編集AIが利用できなかった」と正直に言う）

フォールバック紙面になった日は、Actionsログの
「編集AI(gemini)が失敗したためフォールバックします: (理由)」の行で原因が分かる。
理由のログ出力が生命線なので、握りつぶす変更をしてはならない。

## 3. 指示書（prompts/editor.md）の扱い方

**プロンプトはコンテンツである。** 号JSONに promptHash が記録され、diffが編集方針の歴史になる。

### 実運用で得た掟

- **例文を書くと、それは例ではなく雛形として使われる。**
  「良いテーマの例」に書いた題がそのままコピーされ続けた（#21『静かな技術』は例文と完全一致）。
  例を書くなら「形」の説明にとどめるか、「この指示書に書かれた語をそのまま題にしてはならない」と
  明記する（現在は後者を採用）
- **繰り返しを防ぎたければ、過去の実績を渡す。** 「重複するな」と書くだけでは効かない。
  直近40本のテーマ題をプロンプトに渡すようになって初めて効いた（PR #8）。
  Hidden Gemの30日再掲禁止と同じで、記憶はシステムが持ち、判断だけAIに渡す
- **優先順位を明示する。** 重複回避を強く書きすぎると実態に合わない題をひねり出す。
  「題が紙面の実態に合っていることが最優先、重複回避はその次」と順位を書く
- **キーワードは索引であると教える。** 用途（夕刊の星図の原料）を書き、名詞句のみ、
  括弧不可、表記ゆれ注意を指示する。それでも出る断片は keywords.mjs が発行前に落とす

### 変更の反映

発行workflowが読むのはmainのみ。prompts/editor.md をmainへpushすれば次号から反映される。
テーマや文体の変化は数号ぶんの実物で判断する（1号では編集のゆらぎと区別できない）。

## 4. よくある失敗モードと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| 全モデル404 | モデル世代交代。旧モデル名は新規APIキーで404になる（ListModelsに出るのに呼ぶと404の罠あり） | editor.models を現行世代へ差し替える。「-latest」系を残しておくと延命しやすい |
| 混雑時間帯の503連発 | 本番サイズのリクエストだけ落ちる（小さいリクエストは通るため気づきにくい） | lite系がフォールバック後段にある限り自走する。恒常化したら発行時刻をずらすか本命モデルを変える |
| empty response | セーフティフィルタや空応答 | リトライとモデルチェーンが吸収する。頻発したらプロンプトの表現を点検 |
| テーマが似てくる | 語の癖（「手」「道具」など）。実績を渡しても語彙の重心は残る | Actionsログの「テーマが過去号と重複しています」警告を見る。完全一致や包含のみ検出対象。語の頻用が気になったら指示書の「良い題の形」を調整 |
| フォールバック紙面が続く | キー失効、無料枠の変更、恒久的なAPI変更 | SETUP.mdのキー再発行手順。GEMINI_API_KEYはリポジトリsecret |

## 5. 安全に試す方法

- **mockプロバイダ**: `EDITOR_PROVIDER=mock` で編集AIなしの決定論的な編成が走る。
  パイプライン変更のテストはまずこれで通す
- **注意**: `npm run dry-run` は `--force` 付きで当日の朝刊を**上書き発行**する
  （冪等設計のため号数は再利用される）。ローカルで実行すると public/data/ が変わるので、
  試したあとは `git checkout -- public/data data` で戻すか、コミットしない
- **単発の本番再発行**: GitHub Actionsの workflow_dispatch を手で叩く（同日同版は上書き、安全）

## 6. 点検コマンド

```
発行runの一覧（イベント別。workflow_dispatchがscheduler経由）
  gh run list --repo yzrswork/yzrs-times --limit 12 \
    --json name,event,createdAt,conclusion

失敗runのログからフォールバック理由を探す
  gh run view <run-id> --repo yzrswork/yzrs-times --log | grep "フォールバック"

号の出自（どのモデルが編集したか）
  public/data/issues/YYYY-MM-DD-<edition>.json の generator.provider / model / promptHash
```

正常運転の目安: provider が gemini、model が editor.models の先頭付近、
発行時刻が朝刊5:17 JST、昼刊11:47 JST の数分以内（scheduler経由。2026-07-28実測で数秒精度）。
